Mes vérifications — 16 novembre 2026

J'ai utilisé Windows et des conteneurs Linux amd64 avec Podman 5.7.1 et Docker Compose standalone 5.0.2.

J'ai validé :
- la construction des images PHP/Apache et MariaDB ;
- docker-compose config --quiet ;
- la syntaxe des quatre fichiers PHP avec php -l ;
- les tests HTTP : santé, consultation, création, méthode 405, CSRF 403, champs invalides 422, longueur et échappement XSS ;
- l'exécution du Web sous uid=33(www-data), avec read_only et cap_drop ALL ;
- l'initialisation SQL sur un volume neuf et la connexion PDO entre les services ;
- la persistance de l'article après down puis recréation, avec les deux services healthy.

J'ai publié les images mouedrhi492/ynov-articles-web et mouedrhi492/ynov-articles-db avec latest et le SHA 8d39914b870aee697761d49b1a947eefedbd5786. J'ai vérifié leur accessibilité publique ; les digests sont dans publication.json. J'ai réalisé cette publication manuellement avec Podman.

J'ai ensuite exécuté Trivy sur les deux images publiées. Le Web présente 147 résultats HIGH et 5 CRITICAL, dont 4 critiques avec correctif. MariaDB présente 25 HIGH et 1 CRITICAL, avec correctif. Le scan est terminé, mais le seuil de sécurité CI n'est pas validé. Les rapports complets sont inclus dans docs/.

J'ai poussé le code sur github.com/Mouedrhiri/docker-articles et configuré les secrets Docker Hub. Une première exécution du workflow a échoué pendant la préparation à cause d'une référence Trivy inexistante. J'ai corrigé cette référence vers le commit officiel de v0.36.0. Les exécutions sont consultables dans Actions. La correction des vulnérabilités détectées reste à effectuer.

Sur mon environnement Podman, j'utilise DOCKER_API_VERSION=1.44 pour la compatibilité du client Compose. Les healthchecks sont déclarés dans Compose afin de fonctionner aussi avec les images au format OCI.
